# `at`: a one-shot scheduler for Home Assistant (design)

Date: 2026-11-17
Status: draft, awaiting approval. Builder check done, and the author's answers are folded in.

## 1. Intent

`at` is a Home Assistant custom integration (domain `at`) that works like the Unix `at`
command. It runs an action, a script, or an automation once at a set time and keeps a
record of what happened. You drive it by voice (Assist, both the built-in agent and LLM
agents), from a sidebar panel, from dashboard entities, and through actions (services)
in automations and scripts.

**Why it needs to exist.** HA's built-in "delayed commands" only take relative times. You
can't list or cancel them, and they create no entities. scheduler-component is built for
recurring weekly schedules and has no voice support. delayed_action and the forum "Scheduled
Action" have no voice support and are thinly maintained. Blueprint and `input_datetime`
tricks need manual bookkeeping for every job. Core maintainers have declined to add this.
Nothing on offer combines absolute and relative times by voice, a persistent queue you
can list and cancel by voice and UI, history, and entities other things can use.

**Audience.** It's distributed publicly (HACS) and must work on any HA install with any
Assist pipeline: the built-in agent, an LLM agent, and "prefer local intents" on or off.
Nothing may assume the author's own setup.

## 2. Goals, non-goals, anti-goals

**Goals (v1)**
- Schedule by voice with relative and absolute times in either word order:
  "at 11pm turn on the master bathroom light", "turn on the master bathroom light at 6am",
  "in 30 minutes run the bedtime script".
- List and cancel by voice: "what's scheduled?", "what's scheduled for tonight?",
  "cancel the 6am job", "cancel the master bathroom light", "cancel everything scheduled".
- A persistent queue that survives restarts, with defined handling for jobs missed during downtime.
- History of done, failed, cancelled and missed jobs, with results and configurable retention.
- A dedicated sidebar panel to list, add, cancel, run now, re-schedule, and browse history.
- Entities for dashboards and automations: a to-do list, a next-job sensor, and a pending-count sensor.
- Actions: `at.schedule`, `at.list`, `at.cancel`, `at.run_now`, `at.clear_history`.
- Events and logbook entries for the job lifecycle.

**Non-goals (v1)**
- Recurring schedules (use automations or scheduler-component).
- Conditions on jobs ("only if someone is home"). Possibly v2.
- Languages other than English. The structure must allow them; see §9.
- Commands only an LLM understands, like "make the living room cozy". v1 refuses them (§5.2).
- A dashboard card. That's on the roadmap (§12).
- Extra confirmation for sensitive domains such as locks and alarms. If Assist would do it now, `at` does it later.

**Anti-goals: things that would make it a failure even if it technically works**
- An LLM decides the time. Time parsing must be deterministic and local.
- A job fails silently at fire time when the problem could have been caught when it was
  created ("which light?" must surface while the user is still talking).
- Install requires users to edit config files, create automations, or install a second
  HACS item before voice works.
- It writes into the user's `config/` directory.
- Voice reaches entities that aren't exposed to Assist.

## 3. Constraints

- Start from https://github.com/jpawlowski/ha-integration-blueprint. Keep its structure,
  devcontainer, tooling (uv, Ruff, Pyright, pytest-homeassistant-custom-component, prek,
  Release Please) and conventions. It targets HA 2026.10+ and Python 3.14.
  Run `initialize.sh --domain at`.
- Leave the display name in `manifest.json` as a placeholder. The author will set it.
- Don't copy code from existing projects (scheduler-component, delayed_action, and so on).
- Must be installable through HACS in one step, so the built frontend bundle is committed
  inside `custom_components/at/`.
- English only in v1, without baking English into the core logic.

## 4. Approaches considered and decisions

### 4.1 What a job stores and runs
| Option | Trade-off |
|---|---|
| A. Save the sentence and replay it through Assist at fire time (how delayed commands work) | Simple, and anything the agent can do works. Nothing is checked until it fires, renames break it, and LLM results are unpredictable. |
| **B. Save the intent as recognized when the user spoke** (intent type and slots) and run it through HA's intent handler at fire time | **Picked for voice.** Errors surface right away. Areas, floors and device classes work the way they do in Assist. Needs HA's "recognize without executing" internals. |
| **C. Save a plain action call** (HA script action config) | **Picked for UI and `at.schedule`.** The most predictable and readable. Rebuilding HA's intent handling for voice would be too much work. |

**Decision:** two job kinds in one queue: `intent` (from voice and LLM, and from typed text
in the panel or to-do) and `action` (from pickers and services). Option A is a **roadmap
item** that would cover commands only an LLM understands.

### 4.2 How voice sentences reach Assist
| Option | Trade-off |
|---|---|
| **1. Register sentence triggers programmatically on the default agent at setup** | **Picked.** Works with no setup on any pipeline. Relies on HA internals. |
| 2. Write a `custom_sentences/` file into the user's config dir | Uses only documented mechanisms, but it's intrusive: file clashes, reloads, leftovers after removal. Breaks the anti-goal. |
| 3. Users create sentence triggers (for example from a blueprint) | Supported, but extra setup per user and nothing for LLMs. Wrong for a distributed integration. |

**Decision:** Option 1. In addition, `at` registers intents (`AtSchedule`, `AtList`,
`AtCancel`) so LLM agents get them as tools through HA's Assist API. The sentence-trigger
callback calls the same intent handlers, so there's one code path.

### 4.3 UI
| Option | Trade-off |
|---|---|
| To-do list entity | Built-in card with no frontend code. Its "complete" semantics are awkward. |
| Calendar entity | Nice timeline, but no countdown, slow cancel, and a meaningless end time. |
| Dedicated card | Best UX for dashboards. Needs a frontend build. |
| **Sidebar panel** | Required by the author: cards and actions alone aren't enough. |

**Decision:** v1 ships a **sidebar panel** (layout A: tabs plus an Add dialog, below), a
**to-do list entity**, and **two sensors**. The **dedicated card** is on the roadmap and
reuses the panel's components. A calendar entity is a possible later read-only view.

### 4.4 Repo shape
One repo. Panel source is in `frontend/` (TypeScript + Lit), and the built bundle is
committed to `custom_components/at/frontend/`. Rejected: a separate HACS frontend repo,
because it's a second install.

## 5. Behaviour

### 5.1 Time phrases (v1, English)
- Relative: "in N seconds/minutes/hours/days", "in an hour", "in half an hour",
  "in an hour and a half", "in N and a half hours".
- Clock: "at 11pm", "at 11 pm", "at 6:30", "at 6:30 am", "at noon", "at midnight",
  "at 7 o'clock".
- Day words: "tonight", "this evening", "this afternoon", "this morning", "tomorrow",
  "tomorrow morning", "on <weekday>". Combined with a clock time ("tomorrow at 7",
  "at 6:30 tonight", "on Friday at 8").
- Not in voice v1: calendar dates ("December 3rd"). The panel date picker covers them.

**Rules**
- An hour with no AM/PM gives the next occurrence of that hour, AM or PM, whichever comes first.
  "tonight" and "this evening" force PM; "morning" forces AM; "this afternoon" forces PM.
- An absolute time that has already passed today rolls to the next day. The spoken
  confirmation says so ("tomorrow at 6 AM").
- "tomorrow at 7" with no AM/PM gives the first 7 o'clock tomorrow, which is 7 AM.
- "on <weekday>" means the next such day. If it's today and the time hasn't passed yet,
  it means today.
- All local times use HA's configured time zone and are stored as UTC instants.
  A non-existent local time (spring forward) moves forward to the first valid minute. An
  ambiguous time (fall back) uses the first occurrence.
- Relative times are exact durations from "now" ("in 2 hours" across a DST change is
  still 120 minutes).
- Confirmations always state the resolved time: "OK, at 6 AM tomorrow I'll turn on
  Master Bathroom Light." Relative times also state the clock time: "OK, in 20 minutes,
  at 10:42 PM, I'll run Bedtime."

**Parser:** hand-written and pure Python, with no HA dependencies and no date library. It
takes either structured slots from sentence matching or free text (panel, to-do, the
LLM `time` slot, the `at.schedule` `when` text) plus `now` and a tz, and returns
`{due_utc, rolled_over: bool, spoken: str}` or a parse error. Phrase words live in a
per-language table.

### 5.2 Voice (built-in agent via sentence triggers)
Sentence patterns use number range lists for the time pieces and a wildcard `{command}`
for the rest, in both word orders. Examples:
`at {hour}[:{minute}] [{ampm}] {command}`, `{command} at {hour}[:{minute}] [{ampm}]`,
`in {n} (minutes|hours) {command}`, `{command} in {n} (minutes|hours)`,
`[tomorrow|tonight|on {weekday}] ...`.

**Scheduling flow**
1. The trigger fires with time slots and `{command}` text.
2. The time is parsed (§5.1).
3. `{command}` goes through the default agent's *recognize-only* path, with the same
   language, device_id and satellite area as the original request.
4. **Refuse** if there's no intent match, if the matched intent is itself an `at` intent,
   or if it's a timer, delayed-command or query intent ("what's the temperature"). In
   that case, answer: "Sorry, I can only schedule commands I can check right now. Try
   rephrasing, or schedule a script or scene."
5. **Refuse** if no exposed entity matches the targets: "I couldn't find a light called
   bathroom." Reuse HA's own error wording where it's available.
6. Create the job and reply with the confirmation.

**List.** "what's scheduled", "what's scheduled for (tonight|today|tomorrow)", and
"what's scheduled for <name>". Read up to 3 jobs in time order, then "and N more".
If there are none: "Nothing is scheduled."

**Cancel**
- By time: "cancel the 6am job" or "cancel the job at 6".
- By target: "cancel the master bathroom light", matched against job summary or target names.
- All: "cancel everything scheduled" or "cancel all jobs", which cancels everything and
  reports the count.
- Exactly one match: cancel it and confirm.
- Several matches: cancel nothing and reply listing them ("There are 2 jobs for Master
  Bathroom Light, at 6 AM and 11 PM. Say 'cancel the 6 AM job'."). *(Builder's call:
  single-turn disambiguation. Multi-turn follow-up is a later improvement.)*

**Overlap with HA's built-in delayed commands.** *(Author's decision.)* `at` registers
the relative-time patterns ("{command} in N minutes", "in N minutes {command}"). Sentence
triggers match before intents, so these take over HA's delayed-command and timer behaviour
for those phrases. Relative jobs then appear in the queue and can be listed and cancelled.
The option **"Let HA handle relative-time commands"** (default **off**) skips registering
the relative-time patterns so HA's built-in behaviour returns. Absolute-time patterns
are always registered. Plain timer sentences that don't contain a command ("set a timer
for 5 minutes") are never registered by `at`.

**Prefer-local and LLM pipelines.** Sentence triggers are matched by the built-in agent.
With an LLM agent and prefer-local off, the LLM uses the `AtSchedule`, `AtList` and
`AtCancel` tools. Intent descriptions must tell the LLM to pass the time phrase verbatim
and the command as a plain Assist sentence, and never to run the command itself.

### 5.3 Execution
- **Intent jobs:** call HA's intent handling with the stored intent type, slots, language,
  `device_id` and `assistant=conversation` at fire time, so exposure is checked again.
  The context carries the creating user.
- **Action jobs:** run the stored action list as an HA script (`script.Script`) with the
  creating user's context. `script.turn_on` with variables and `automation.trigger` are
  just action jobs.
- Status flow: `pending → running → done | failed`. Also `pending → cancelled` and
  `pending → missed`.
- A failure saves the error text in `result.error` and fires `at_job_failed`.
  There is no automatic retry.
- Actions that take a long time don't block the scheduler: each job runs as its own task.

### 5.4 Scheduling and restarts
- One `async_track_point_in_utc_time` per pending job, plus a **once-a-minute sweep**
  that fires any pending job whose due time has passed. This guards against wall-clock
  jumps, because the loop timer uses monotonic time.
- On startup, load the store and look at each pending job:
  - Due in the future: schedule it.
  - Overdue by no more than the **grace window** (option, default 5 min): run it now.
  - Overdue by more: mark it `missed` and fire `at_job_missed`.
- Jobs created by voice or the panel run as the user who created them. A job whose user
  has been deleted runs with a system context. *(Builder's call.)*

### 5.5 Permissions
- `at.schedule` with a raw `action` is **admin-only** when a user calls it. Automations
  and scripts are unaffected. `at.schedule` with `command` (text) is open to all users.
- The panel is visible to all users. An option makes it admin-only (default off). Only
  admins see the raw-action (YAML) mode in the Add dialog.
- Voice can only reach entities exposed to Assist, both when a job is scheduled and when it fires.
- **One shared household queue.** *(Author's decision.)* Every user, through voice, panel,
  to-do or services, sees every job and can cancel any job.
  - Voice "cancel everything" skips jobs created through `at.schedule` (`source.via ==
    "service"`), so one spoken command can't break automations. The reply says how many
    were skipped. They can still be cancelled one at a time, or from the panel, to-do or service.
  - Run now and re-schedule of `action` jobs that hold a raw action are admin-only.
    *(Builder's call.)*
- **"Pick it" validation on the server.** *(Builder's call.)* For non-admins, `at/schedule`
  and to-do creation only accept these action shapes:
  - `homeassistant.turn_on`, `homeassistant.turn_off` or `homeassistant.toggle` (or the
    domain equivalent) on targets, with no extra data
  - `script.turn_on` with variables
  - `automation.trigger`
  
  Anything else is rejected. Targets may be any entity: dashboards already allow that, and
  the exposure limit applies to voice only.

## 6. Data model

Store: HA `Store`, key `at.jobs`, `version 1`, `minor_version 1`, with a migration hook
from day one.

```
Job {
  id: str               # short random id, e.g. 8 hex chars
  kind: "intent" | "action"
  status: "pending" | "running" | "done" | "failed" | "cancelled" | "missed"
  due: ISO UTC
  created_at, finished_at: ISO UTC | null
  summary: str          # "Turn on Master Bathroom Light"
  original_text: str | null   # what was said or typed
  intent: { type, slots, language, device_id, satellite_id } | null   # kind=intent
  action: list[dict] | null                                           # kind=action
  targets: { entity_ids:[], area_ids:[], floor_ids:[] }  # best-effort, for display & cancel-by-name
  source: { via: "voice"|"llm"|"panel"|"todo"|"service", user_id, device_id, agent_id }
  result: { error: str | null, cancelled_by: str | null }
}
```

History retention defaults to 7 days or 100 entries, whichever limit hits first. Both are
options. It's pruned on startup and after each job finishes.

## 7. Interfaces

### 7.1 Actions (services)
- `at.schedule`: exactly one of `command` (text, parsed like voice) or `action` (action
  list, admin), plus exactly one of `at` (datetime), `delay` (duration) or `when` (time
  phrase text). Optional `name` overrides the summary. Returns `{job_id, due, summary}`.
- `at.list`: returns pending jobs plus history, filterable by `status` and a time range.
- `at.cancel`: `job_id` (one or a list) or `all: true`.
- `at.run_now`: `job_id`. Runs the job now and records it in history.
- `at.clear_history`.

### 7.2 Events
`at_job_scheduled`, `at_job_executed`, `at_job_failed`, `at_job_cancelled` and
`at_job_missed`. The payload has `job_id`, `summary`, `due`, `status` and `source.via`.
A logbook platform describes each one.

### 7.3 Entities
One config entry (`single_config_entry: true`) and one service-type device.
- `todo.at_scheduled`
  - Items are pending jobs (summary plus due), followed by completed items for recent history.
  - Creating an item parses its text the way the panel's "Type it" does.
  - Deleting an item cancels the job. Changing its due date reschedules it.
  - Ticking off a pending item runs it now. *(Decision: the most natural meaning of "complete.")*
- `sensor.at_next_job`: a timestamp sensor holding the next due time. Attributes: job_id, summary.
- `sensor.at_pending_jobs`: the count. Attribute: the compact pending list.

### 7.4 WebSocket API (for the panel)
`at/subscribe` (full snapshot, then deltas), `at/schedule`, `at/cancel`, `at/run_now`,
`at/reschedule` (copy a history job with a new time), `at/parse` (preview for "Type it":
returns the resolved summary and due time, or the refusal text, without creating
anything), and `at/clear_history`. Admin checks follow §5.5.

### 7.5 Sidebar panel (layout A)
Register it with `panel_custom` and serve the bundle from a static path, with a version
query string for cache busting. Sidebar title: "at" (placeholder; follows the display name).
- **Header:** tabs **Upcoming (n)** and **History**. Buttons: **+ Add job**, and a ⋮ menu
  with "Cancel all" and "Clear history".
- **Upcoming** columns: When (live countdown under 1h, otherwise a local time or
  weekday plus time), Job, Source (voice + device / user / service), and actions ▶ run now, ✕ cancel.
  Clicking a row shows details: the full stored action or intent, creator and created time, and the id.
- **History** columns: status icon (✓ done, ✗ failed, ⚠ missed, ⊘ cancelled), time, job,
  and result or error. Filter by status. Row action: **Re-schedule**.
- **Add job dialog:**
  - "Type it": a text box with a live `at/parse` preview.
  - Or "Pick it": a target picker, an action picker (turn on/off/toggle for the target's
    domains, run script with variables, trigger automation), and admin-only raw YAML.
  - When: quick chips (+15m, +1h) or a date-time picker.
  - The author says the dialog will be revisited. Ship it as described.
- Live updates over `at/subscribe`. Follows HA theme CSS variables, including dark mode.

## 9. Languages
Sentence templates, time phrase tables and response strings are in per-language modules
keyed by language code. Only `en` ships. Core logic never contains English words. Panel
strings use the integration's frontend translation mechanism or a simple per-language
dictionary (builder's call).

## 10. Risks and things to verify first (go/no-go spike)
These depend on HA internals. Each must be proven on HA 2026.10+ before the dependent
phase starts. The findings go into `ha_internal/` with tests that fail loudly if HA changes.
1. Programmatic sentence-trigger registration on the default agent, with wildcard plus
   range-list slots, in both word orders.
2. Recognize-only for a sentence, with device/area context, that returns intent and slots
   without running anything, and tells us when no exposed target matches.
3. Running a stored intent and slots later through HA's intent handling.
4. Custom integration intents show up as tools in HA's Assist LLM API.
5. Sentence triggers fire on a pipeline using an LLM agent with prefer-local on.
6. `panel_custom` registration from a custom integration, and which HA frontend elements
   (`ha-selector` target/action pickers) a custom panel can load reliably. If the pickers
   can't be loaded reliably, ship a simpler built-in entity and action picker.

**If a check fails** *(builder's calls, except where noted)*:
- **1, 2 or 3:** stop and bring options back to the author. The voice design rests on these.
  Don't fall back to writing into `config/`, and don't convert intents into action jobs
  without asking.
- **4** (intents not offered to LLMs): LLM support moves to the roadmap. Built-in voice ships.
- **5** (triggers don't fire with an LLM agent and prefer-local on): that setup uses the
  LLM tools only. Document it.
- **6:** ship the simpler built-in pickers described above.

## 11. Testing
- **Time parser:** large parameterized table, frozen "now", America/Chicago and
  Europe/Berlin, the DST change days, roll-over, and AM/PM inference.
- **Scheduler:** freezer/time travel; fire, cancel, run now, sweep after a clock jump.
- **Restarts:** with the `hass_storage` fixture, cover pending jobs restored, grace-window runs and missed jobs.
- **Voice:** `conversation.async_converse` against test entities for each sentence in
  §5.2, both word orders, refusals, unexposed entities, and cancel disambiguation.
- **Services, WebSocket, entities, events and logbook:** standard HA test fixtures.
- **Frontend:** type-check, lint, and unit tests for time and countdown formatting. A
  manual check in the devcontainer HA for the panel.

## 12. Roadmap (not v1)
